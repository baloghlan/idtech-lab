# IDTECH Academy — Ansible Infrastructure Automation Lab

## Overview

This project demonstrates infrastructure automation with Ansible across two Ubuntu 22.04 virtual machines running on an Arch Linux host using Incus.

Ansible manages the control node itself, configures the application server, deploys a Python HTTP backend as a systemd service, and configures HAProxy as an HTTP reverse proxy. The lab also demonstrates inventory variables, facts, loops, handlers, service health checks, safe configuration validation, error recovery, and idempotence.

## Architecture

```text
Arch Linux Host (Incus)
│
├── control01 — 192.168.56.11 (Ubuntu 22.04)
│   ├── Ansible control node
│   ├── Managed locally by Ansible
│   └── Project management utilities and artifacts
│
└── app01 — 192.168.56.12 (Ubuntu 22.04)
    ├── HAProxy (0.0.0.0:80)
    │   └── HTTP reverse proxy to 127.0.0.1:8080
    └── Python HTTP backend (127.0.0.1:8080)
        └── systemd service: idtech-backend
```

| Node | IP address | Operating system | Purpose | Ansible connection |
|---|---|---|---|---|
| `control01` | `192.168.56.11` | Ubuntu 22.04 | Ansible control and managed node | `local` |
| `app01` | `192.168.56.12` | Ubuntu 22.04 | HTTP backend and HAProxy | SSH |

Both VMs use the Incus `incusbr0` network (`192.168.56.0/24`). The lab backend is bound to loopback; external HTTP traffic reaches it through HAProxy on `app01` port `80`.

## Technologies

- Arch Linux and Incus for VM provisioning
- Ubuntu 22.04 LTS on both VMs
- Ansible 2.10.8
- Python 3 and the Python standard-library HTTP server
- HAProxy, systemd, and Jinja2
- SSH for remote management

## Ansible Configuration

The inventory is organized into `control_nodes` and `app_servers` groups. Shared settings are in `inventory/group_vars/all.yml`, while node-specific settings are in `inventory/host_vars/`.

Examples of configurable values include the backend bind address and port, the HAProxy frontend port, the backend response message, managed user/group names, and project paths. The playbook uses three plays:

1. Apply `common` to both VMs.
2. Apply `control_node` to `control01`.
3. Apply `backend` and `haproxy` to `app01`.

### Roles

| Role | Target | Responsibilities |
|---|---|---|
| `common` | Both VMs | Install common utilities, create the `idtech` group/user, and use loops and OS facts |
| `control_node` | `control01` | Create `/opt/idtech-ansible`, install `tree` and `jq`, and generate a node-information artifact |
| `backend` | `app01` | Create a dedicated service user, deploy Python code and a systemd unit, manage the service, and validate HTTP health |
| `haproxy` | `app01` | Install HAProxy, render its Jinja2 configuration, validate a candidate before activation, reload on changes, and handle invalid configuration safely |

The backend role checks `GET /` with `ansible.builtin.uri`, registers the result, retries when necessary, and asserts the expected response. HAProxy is configured with a backend health check and a reload handler.

## Deployment and Verification

### Prerequisites

- Arch Linux host with Incus configured and the two lab VMs provisioned
- Working network connectivity between the VMs
- Ansible installed on `control01`
- Python 3 available on the managed nodes
- SSH key authentication from `control01` to `app01`
- Passwordless sudo access for the Ansible user

VM provisioning is performed on the **Arch Linux host** using `init-vms.sh`. The provisioning script is included in this repository; review its settings before running it in a different environment.

All Ansible commands below are executed on **`control01`**, from its project directory:

```bash
cd /home/ubuntu/ansible-lab
```

Verify inventory connectivity:

```bash
ansible all -m ping
```

Check playbook syntax:

```bash
ansible-playbook playbooks/site.yml --syntax-check
```

Deploy the full configuration:

```bash
ansible-playbook playbooks/site.yml
```

Git operations and screenshot organization are performed on the **Arch Linux host**, not on `control01`. The Git checkout stores the Ansible project under `ansible/`, while the working copy on `control01` is `/home/ubuntu/ansible-lab`.

## HTTP Backend

The backend is a small Python HTTP server managed by systemd under the dedicated `idtech-backend` user. It listens on `127.0.0.1:8080` and responds to `GET /` with JSON containing the configured message and hostname.

Example response:

```json
{
  "message": "Hello from IDTECH Academy!",
  "hostname": "app01"
}
```

On `app01`, verify the backend service and its direct response:

```bash
sudo systemctl status idtech-backend --no-pager
curl -i http://127.0.0.1:8080/
```

## HAProxy

HAProxy listens on port `80` on `app01` and forwards requests to the local backend at `127.0.0.1:8080`.

From `control01`, verify the proxied response:

```bash
curl -i http://192.168.56.12/
```

Expected result: HTTP `200 OK` and the JSON response shown above.

On `app01`, verify HAProxy service state and configuration syntax:

```bash
sudo systemctl is-active haproxy
sudo haproxy -c -f /etc/haproxy/haproxy.cfg
```

## Safe Configuration Failure Test

The HAProxy role uses an Ansible `block` / `rescue` / `always` sequence to validate a candidate configuration before replacing the active one.

For the failure test, the invalid directive `incorrect_syntax` was temporarily appended to `roles/haproxy/templates/haproxy.cfg.j2`. Running the playbook caused the candidate validation command to fail. The rescue tasks reported the error and marked the deployment as failed, while the always task removed the temporary candidate file.

**Observed result:** the existing active HAProxy configuration was preserved, `systemctl is-active haproxy` still returned `active`, and HTTP requests through HAProxy continued to return `200 OK`.

The invalid directive was removed after the test, and the playbook completed successfully again. The intentionally invalid configuration is **not** included in the final project.

## Idempotence Test

After restoring the valid configuration, the complete playbook was executed twice consecutively. Both executions completed with `changed=0` and `failed=0` on each node.

| Node | OK | Changed | Failed |
|---|---:|---:|---:|
| `control01` | 8 | 0 | 0 |
| `app01` | 18 | 0 | 0 |

These results demonstrate idempotence for the tested lab state.

## Security Notes

- SSH private keys, passwords, and access tokens must not be committed to the repository.
- The backend runs under a dedicated system account and binds only to loopback.
- HAProxy configuration is checked before the active configuration is replaced.
- Shared and host-specific settings are maintained in Ansible inventory variables.
- The environment is intended for an isolated training lab; production deployments would require additional network, TLS, and security hardening.

## Conclusion

This lab demonstrates repeatable Ansible management of two Linux VMs, including backend deployment, systemd service management, HAProxy reverse proxying, health checks, configuration validation, safe failure handling, and idempotence.
